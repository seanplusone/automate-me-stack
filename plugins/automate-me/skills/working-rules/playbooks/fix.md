# Fix a ticket

The default plan for `fix <ticket>`. The user's own steps, when given, replace it. Stop at each CHECKPOINT: finish the step, make a `wip:` commit, update `RESUME.md`, and wait for the user. A `<profile: ...>` value comes from the project's `.claude/project-profile.md`.

1. **Worktree.** Fetch `<profile: base_remote>`. Create `.worktrees/<key lowercased>` on a new branch `<KEY>-<short slug from the summary>` off `<profile: base_remote>`/`<profile: base_branch>`. Copy in the gitignored runtime files the profile lists in `<profile: worktree_copy>` (real copies, not symlinks), and run `<profile: worktree_check>` to confirm the worktree resolves its own code, not the main checkout's. Start `RESUME.md` at the worktree root. Git does not ignore it inside a worktree, so add `RESUME.md` to the repo's `.git/info/exclude` once.
2. **Read.** The ticket (`<profile: ticket_view>`, skipped when a hook already put it in context) and its comments (`<profile: ticket_comments>`), the repo's rules, and the files the ticket names. Say which other file you open and why before opening it. After about ten files without an answer, stop and ask where to look.
3. **Validate on the base branch.** Is the bug still true, is the scenario real, and does any proposed patch hold? Cite `file:line`. Measure what every fix option depends on, not only the one you recommend. Find every reader of a changed value by its shape and by hooks that walk the whole payload, not only by its name (`python3 "$SKILL_DIR"/../shared/client_sweep.py <field> --repo <name>=<path>`, then read what it lists). The field is the data key the change reads or writes, not the ticket key. Pass one `--repo` per client checkout in `<profile: client_repos>`. Set `--marker` to that value's own shape. Set `--carrier` to the payload name it travels in, or leave it off. A claim that something has no effect holds only after a check on every client that reaches the code (`<profile: clients>`).
4. **CHECKPOINT.** An artifact page with the symptom, the cause, the fix options, the open decisions and the test plan. An open condition goes under every option it affects, in the words of the ticket or comment that raised it. A recommendation that makes it moot does not settle it. Wait for the user's answers.
5. **Reproduce.** A test that fails on the base branch, using the ticket's records where they exist locally. Run it with `<profile: test_one>` from the worktree. Reproduce in the browser where the user sees the bug, on `<profile: app_url_test>`, with `/automate-me:verify-web`. Save the setup as a verify-web recipe so the after run uses the same data. Read any rows you need through `/automate-me:query-db`.
6. **CHECKPOINT after the smallest fix** that matches the user's answers. Map the blast radius first, with the repo's change checklist when it has one (`<profile: change_checklist>`). While iterating, run only the test you touched, with `<profile: test_one>`. Check that the command runs the worktree's code and not the main checkout's. When the test command does not migrate the test database, a fix that adds a migration runs it first (`<profile: test_notes>`). Before the PR, run the whole suite against the worktree with `<profile: test_full>`. When a suite run dies partway, split it the way the profile's test notes say, and report which part died. The test passes, and fails again with the fix reverted. Write every test the ticket or a reviewer asked for. When the chosen fix changes a test's expected result, write it with the new assertion and say so. A browser check is extra evidence, not a replacement.
7. **Prove it.** Before and after in the browser on the same data, changing only the code, with screenshots. Check the path the ticket says must not change, on every client that reaches it.
8. **CHECKPOINT after the PR.** Ask the user to type `/automate-me:open-pr`, which only they can start. Then run `/automate-me:review-pr` on it, and the repo's own review skill when the profile names one (`<profile: review_skill>`). Apply the fixes and re-verify them.
9. **Wrap up.** Update the artifact with the verified results, remove any local overrides you added, and give the PR URL. Keep the bug's repro data until the PR merges.
