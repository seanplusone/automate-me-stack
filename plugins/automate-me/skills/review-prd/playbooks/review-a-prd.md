# Playbook: Review a PRD

Input is one PRD. Output is a block of open questions that the engineer checks row by row. A person adds it as one section at the bottom of the PRD. A separate list goes to the design doc. A question reaches the block only if it passes the test in the root `SKILL.md`. Without an answer, the engineer would have to guess what a user or customer sees, is told, waits for or loses. Copy these steps into the todolist word for word. A skipped step stays as `skip: <reason>`.

## Steps

1. **Build the mind map.** Run `skills/prd-mindmap`. A person checks the map before step 2.
2. **Tag operations.** Run `skills/prd-gaps` step 2. The scenarios in step 3 read these tags to find missing operations, so they must exist first.
3. **Scenarios.** `check.py scenarios out/gaps.txt ../shared/rules out/map.txt` lists every scenario the rules produce. Rules in `../shared/rules/` fire on every PRD, on missing operations, or on the map's shape. It fails if `out/gaps.txt` has no tags yet. `skills/prd-gaps` step 3 fills each with a PRD quote or "not stated". `check.py check-scenarios` fails if one is missing or invented.
4. **Gaps.** Run `skills/prd-gaps` steps 1 and 4.
5. **Collisions.** Run `../find-prd-collisions` on `out/map.txt` and `out/gaps.txt`. It finds points that contradict each other and scenarios that fall between points, which step 4 cannot see because it checks each point alone. Write its output to `out/collisions.md`. Its 15-question cap does not apply here. Its questions are input for step 6, not text for the PM. Step 6 writes every PM question.
6. **Draft questions.** Load `../shared/writing-rules.md` and `../shared/voices/pm.md` first.
   - Before drafting, list what the PRD treats as already built or describes as today's behavior, and check each in the product's code. Write one row each to `out/built.txt`: `<PRD quote> | built, partly built or not built | <file:line or table.column>`. Nothing about a part that is built and that the PRD leaves as it is becomes a question. When the PRD describes today's product wrongly, and the difference changes what gets built, that is a candidate.
   - Before drafting, list how the PRD names the product, the customer organization and each kind of person. Write one row each to `out/terms.txt`: `<what> | <the PRD's term> | <other names it uses, comma separated>`, with rows named `product` and `customer`. `check.py terms <prd> out/terms.txt` counts every name and fails if another name is more common than the term. Load `out/terms.txt` and use only its terms. Never call someone by a job title the PRD uses that the product has no role for.
   - Write every label the PRD coins for its own mechanisms, such as a field direction, a status badge or a named setup step, to `out/prd-labels.txt`, one per line. Questions use a plain term from the glossary instead. A label appears only in the glossary, as "The PRD calls it <label>.", or in a question as `(the PRD calls it "<label>")` when the person will see that exact label on screen.
   - Before drafting, read any engineering design notes or plans for the feature, in the project's own repository or at paths the person names. Never search folders outside them. Don't ask the PM what engineering already decided. A known plan goes in a question only when the ask makes no sense without it, as one short clause after the situation. Never open a question with the plan.
   - Candidates are PM and Unclear wording gaps, not-stated rule scenarios, and PM findings from `out/collisions.md`. A collision marked "already in review" does not stand in for its gap: the gap still needs its own row. Candidates about the same situation become one question, with up to three asks, the way a person would raise them together. Two candidates about different situations stay apart. A candidate the PRD's own open questions already ask stays when engineering's plan adds context that changes the answer, and is asked with that context. Otherwise drop it.
   - Write one row per candidate to `out/questions.txt`: `PM | <question> | <intent: the call the PM is asked to make> | We would guess <what a user or customer would notice, if we guessed wrong>`. Steps 7 to 9 retag rows. Step 11 judges against the intent.
   - Write `out/carried.txt`, one line per PM and Unclear wording gap: `GAP <n> | <its question, exactly as its row in out/questions.txt>`. Gaps merged into one question all point at that row. A gap that becomes no question still gets a row, tagged DROP in step 9 with the reason. `check.py carry out/gaps.txt out/questions.txt out/carried.txt` fails on a gap that reaches no row.
   - A contradiction where neither side is plainly right is a PM question: quote both sides in plain words, then ask which holds. One where one side is plainly right is not a question. It goes to "PRD lines to correct" in `out/for-engineering.md`, both lines quoted.
   - Engineer gaps and Engineer collision findings go to `out/for-engineering.md`.
7. **Check against the PRD.** A worker that did not draft the questions checks every claim in every row against the PRD and quotes the line. An unsupported claim is rewritten or the row dropped. A row the PRD already answers is tagged ANSWERED, with that line as its reason. Search the whole PRD for the answer, not only the lines the row cites: resolved open questions, question-and-answer sections, non-goals and phasing. Two lines that settle it together count, quoted in the reason joined by ` + `. A new question found while checking becomes a new row in `out/questions.txt`, never a note in the worker's output. Before tagging ANSWERED, search for any PRD line that says otherwise, such as a scope cut, a non-goal or a later phase. If one exists, the row is not ANSWERED. It is a contradiction: it goes to "PRD lines to correct" in `out/for-engineering.md` when one side is plainly right, and stays a PM row quoting both lines when it isn't.
8. **Check against the product.** A worker that did not draft the questions lists every noun each row relies on, such as a field, status, action, role or setting. It also lists every claim about what the product does today. It confirms each in the product's code or data and writes `<question> | <noun or claim> | <evidence>` to `out/premise.txt`. The PRD's picture of the product is not evidence. A row that relies on no noun gets `<question> | none | none`.
   - Check in the project's own repository. Read another repository only when the PRD names that product, such as the mobile app. Never read docs or notes folders outside the project. Anything not checked goes under "Not verified".
   - A question states a fact about the product today only when the PM needs it to answer, in one plain sentence. It never says how the product does it or how we would build it.
   - A noun that resolves to nothing is `missing`. One thing is confirmed, with its file:line or table.column. More than one thing is `ambiguous: <thing> at <location>; <thing> at <location>`. For example, a date a user types on a form and a date the product records by itself can share one name. An ambiguous noun is named precisely in the question, or the row becomes a question asking the PM which one the PRD means.
   - A row built on something missing is rebuilt on what exists, or dropped.
   - The PRD may rely on something missing that a user sees or a customer gets. Give it its own row, such as "The PRD sends each record's <value>, but <product> has no such value. Should we drop it from the plan or build it?" A missing internal value, such as a system label or a column, goes to `out/for-engineering.md` instead.
   - Something broken in today's product, such as an update that resets data, goes to `out/for-engineering.md` as a defect.
   - With no code or data to check against, every unchecked noun goes under "Not verified" in the report.
9. **Sort.** Every row keeps exactly one tag:
   - PM: a product or policy call only the PM can make. It passes the test. Without an answer, we would guess what a user or customer sees, is told, waits for or loses. The reason starts "We would guess" and names that. If you can't name it, it is not PM.
   - DESIGN-DOC: engineering decides it, such as time zone handling, merging queued edits, or retrying after an outage. Copy it to `out/for-engineering.md`. Before tagging a row DESIGN-DOC, ask whether its answer decides what a user or admin sees, is told, waits for or loses. If it does, split it: a PM row asking that, in the person's terms, and a DESIGN-DOC row for the mechanism.
   - ANSWERED: the reason is the PRD line that answers it, and no other PRD line says otherwise.
   - DROP: a duplicate, an answer that changes nothing the design decides, or a call engineering's design notes already made. The reason says which.
9a. **Whole-PRD pass.** Steps 4 to 8 read one point at a time, so they miss a gap that shows only when two parts are read together. A worker that did not draft the questions reads the whole PRD, its test plan, any parent PRD it belongs to, and `out/questions.txt`, and looks for:
   - Two things that overlap: a new state, action or setting next to an existing one, or another new one, with no rule for when a user picks which.
   - What an out-of-scope line, a fallback or a "doesn't change" line leaves undefined for a user.
   - The user's next move after each P0 works: undo it, edit it, find it again, explain it to someone.
   - A word a user sees, or a decision hinges on, that the PRD uses as if it were defined.
   - A parent PRD answer the slice drops, contradicts or measures against the wrong baseline.
   A finding that passes the test is a new PM row in `out/questions.txt` and goes through the Rewrites path. One already asked, answered or dropped is not a finding. "None" is a good result.
10. **Pick and write.** Only PM rows go to the PM. Write the report from the root `SKILL.md`.
   - Every PM row goes to the PM. There is no cap. Before writing, reread each PM row against the test. One whose ask is about what the product stores, logs, retries or merges, rather than what a person sees, decides or loses, is DESIGN-DOC. Two rows about the same situation become one, keeping the plainer wording.
   - Size the list to one review meeting: what one engineer would get through with the PM in about half an hour. `check.py pm-list` warns past 25 questions. On the warning, merge questions about the same situation and drop any that fail the test. Never cut by rank. If the list still runs past 25, say so under "Stopped or blocked" with the count.
   - Order by what goes wrong if the guess is wrong. First comes data lost or overwritten without anyone knowing. Next come users blocked, or customers who never turned the feature on. Then the rest. The first 8 at most are "Biggest decisions".
   - Write `out/open-questions.md` from `templates/open-questions.md`. It is the block a person adds as one section at the bottom of the PRD. Every other PM row goes under "Smaller questions, by topic". Each question is the situation, then the ask. It carries no proposed answer, point number, section number, engineering argument or evidence. The heading carries the reviewer's first name and the month. Use `git config user.name` if no one says. The glossary has at most 6 terms, each a plain name, ending "The PRD calls it <label>." when the PRD has one. Number questions as bold text on their own line (`**1.**`), whatever tool the PRD lives in, because Notion restarts a numbered list after each heading. `check.py open-questions out/open-questions.md out/prd-labels.txt` must pass.
10a. **Test plan.** If the PRD links a test plan page, review it as its own document. Check three things against the PRD and the product:
   - Every P0 "Done when" has a test case.
   - Each case's setup can show what the case tests. A setup the product can't reproduce is a correction.
   - Nothing the PRD adds is left untested. That includes behavior the PRD's own open decisions or this review's questions could change.
   A wrong line in the test plan goes to "PRD lines to correct", marked for the test plan page. A missing case, or an expected result only the PM can decide, is a question. A missing case has no line to sit on, so it is never an inline comment. Put several missing cases in one question when they wait on the same answers. A case that only waits on a question already asked on the PRD page is not a new question. Leave it for the answer. Write those to `out/testplan-questions.md` from `templates/open-questions.md`, with the heading "Test plan questions from engineering (<name>, <month>)". It goes in a section at the bottom of the test plan page. It runs through steps 7, 8 and 11 like any question, and `check.py open-questions` and `pm-list` must pass on it. Keep it short. A test plan that covers the PRD gets no questions. Then the file holds only the heading and "No questions.", and nothing is added to the test plan page.
11. **Cold reader.** For each question, one worker sees only that text, its topic heading and the glossary. It restates what the text asks, and reports any sentence it could not restate in its own words and any phrase that sounds technical. A second worker compares the restatement with the row's intent. A mismatch, a sentence it could not restate or a technical phrase fails the row. Reading a sentence twice and then restating it correctly is not a failure. A word the glossary defines is not a technical phrase. A failed row is rewritten and goes back through steps 7 and 8 before it is read again. A row that fails a second time goes to the person: list it under "Stopped or blocked" with both restatements, keep its last version, and move on. Then run the checks in the root `SKILL.md`, report back step 4. Rewrite only the flagged lines.
12. **Panel check.** Run `../shared/skills/panel-check` on `out/open-questions.md`, with these lenses:
   - Completeness: unknowns the PRD needs settled that no question asks.
   - The test: every question would leave the engineer guessing what a user or customer notices. One that doesn't is cut.
   - PM fit: each question is one situation with at most three related asks, PM-owned, answerable without engineering help, plain, and not leading. No proposed answer and no engineering argument.
   - Scope: no question designs the solution or belongs to engineering.
   - Order: "Biggest decisions" are the ones that do the most harm if guessed wrong.
   - Template: `out/open-questions.md` matches `templates/open-questions.md`, and every question reads as a situation, then its asks.
   - Overlap: read every question and correction together, across the PRD and test plan pages. Two items that ask the same thing, or a correction that repeats a question, become one or the weaker one is dropped. Steps 7 and 8 check items one at a time and can't see this.
   Fix what survives the panel. Each fixed or new row goes back through steps 7, 8 and 11. If a question cannot be made one situation, plain and PM-owned, stop and show it to the person.
13. **Engineer review.** Give the engineer one row per PM question: the question, why the design needs the answer (the row's reason), and its PRD quotes and `out/premise.txt` evidence. Each row takes OK, Edit or Drop, and a note. Use an artifact page that saves the choices if the session has one, or a markdown table if not. Read the choices back. A Drop becomes a DROP row with the note as its reason. An Edit is rewritten from the note and goes back through steps 7, 8 and 11. Update `out/open-questions.md` and the report's counts to match, then repeat until every row is OK or Drop. The evidence stays out of `out/open-questions.md`.
14. **Draft out.** Fetch the PRD again from where it lives into `out/prd-now.md`, and run `check.py fresh <prd> out/prd-now.md`. A PRD handed over as a file has no source to fetch, so mark the check `skip: no source`. On FAIL, someone changed the PRD during the review. A changed line can answer a question or move a line a correction quotes. From then on `out/prd-now.md` is the PRD. Run step 7 again on every row and every line in "PRD lines to correct", then the checks in the root `SKILL.md`. Run `fresh` again right before the block or a comment goes on the PRD. Save the report, `out/open-questions.md` and `out/for-engineering.md` as drafts. Never edit the PRD or send anything to the PM. A person adds the block as one section at the very bottom of the PRD the questions belong to. They post each approved line from "PRD lines to correct" as an inline comment on that line. Post the inline comments before adding the bottom section. An anchor matches from its start text to any later copy of its end text, and the section's own questions repeat PRD phrases. End each anchor inside its own line or table cell. Those are the only two additions. Nothing else in the PRD changes.

## Rewrites

Any row rewritten or added after step 8 goes back through step 7, then step 8, then step 11, before it moves on. This holds in every later step, and for a rewrite made after the engineer's review or anyone else's. Keep `out/carried.txt` pointing at the row's new wording. A row gets at most two rewrites. One that still fails goes to the person, as in step 11.

## Stop rules

- PRD missing or empty: stop.
- Map not approved: stop after step 1.
- A panel finding that cannot be fixed after step 12: stop.

## Reply

Write the report from the root `SKILL.md`. Its checks must pass.

## After the PM answers

The PM may answer by editing the line a question was about, or by adding the answer to a questions-and-answers section at the bottom of the PRD. Both count. A question struck through or marked answered in the open questions section counts as answered once its answer is found.

1. Run this playbook again on the revised PRD.
2. For each question in the last `out/open-questions.md`, find its answer: a changed line or an entry at the bottom. List each one with neither as still open, and carry it into the new report.
3. When every question has an answer, the report says so: the PRD is ready for sign-off by the EM, the engineer and the PM.
4. Run `../shared/playbooks/learn-from-run.md`. Questions the PM's answers show we should have asked become proposed rules.
